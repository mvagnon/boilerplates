# Project Technical Instructions

## Introduction

This project is an Expo/React Native application boilerplate.
Give as much information about the project in about ~3-6 lines.

## Project Initialization and Quality Checks

### Post Clone Tasks

After a fresh clone, run from the project root with EAS authentication configured:

```bash
bun install --frozen-lockfile
bun run pull
```

### Run Dev Server

Run the web dev server from the project root:

```bash
bun run web
```

### Cleanup Dev Server

Stop the dev server you started when it is no longer needed.

### Quality Checks

Run static checks from the application directory:

```bash
bun run staticchecks
```

## Architecture

Use a simple, feature-oriented architecture centered around Orval generations.
Do not use wrappers and abstractions around Orval generations.
This layout describes responsibilities, not a file inventory.
Add feature-style folders at the shared level only when genuinely needed across features.

```text
src/
├── app/                              # Router pages/layouts/providers; no feature pages/
├── api/
│   ├── generated/                    # Orval clients, hooks, types and schemas; reuse directly
│   └── http.ts                       # Optional shared transport beyond generated behavior
├── lib/                              # Cross-feature utilities; no more specific owner
├── ui/                               # Shared presentational UI; colocated props/types, no types/
└── features/
    └── <feature>/
        ├── components/               # Feature UI; colocated props/types, no types/
        ├── contexts/                 # Feature contexts/providers
        ├── hooks/                    # Non-API feature state and behavior
        ├── schemas/                  # UI/form validation and inferred types; not API contracts
        ├── utils/                    # Pure feature calculations/transforms
        └── constants/                # Feature constants
assets/                               # Images, fonts and bundled assets
plugins/                              # Expo native config plugins
android/, ios/                        # Generated by Expo prebuild
```

## Other

### Backward Compatibility

- When presenting an implementation plan, flag any changes that cannot preserve backward compatibility.
- Always preserve backend backward compatibility by default: APIs, persisted data, and database migrations must remain compatible with older supported clients.
- Prefer additive changes over multiple API versions. When renaming a field, keep the old field and accept legacy inputs, with one source of truth.
- Database migrations must also support the previous backend version.
- Mark deprecated elements using exactly: `// deprecated on YYYY-MM-DD: <replacement and compatibility reason>`.
- Never remove legacy behavior without explicit approval.
- If backward compatibility is impossible for any reason, explain the breaking change and its impact to the user, and obtain explicit approval **before implementation**.
